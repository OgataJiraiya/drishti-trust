# DRISHTI Full-System Integration

## Architecture and trust boundaries

Dataset, model, inference, and distribution analyzers produce Finding Schema v1 records. The
trusted module process validates those records and signs a `ModuleRunSubmission` with its
registered Ed25519 identity. The backend verifies identity, signature, assessment membership,
and replay state before persisting evidence. The orchestration layer only sequences this flow;
it does not calculate assurance or disposition. The backend summary service is the sole scoring
authority.

Private module keys stay in the trusted module/orchestration process. They are never sent to or
generated by the browser. Signature validity authenticates the submitted bytes and producer; it
does not establish detector accuracy, model safety, or physical-world authenticity.

## Four-module flow

`FullAssessmentOrchestrator` creates and activates an assessment, submits one signed run for
each frozen module identifier, reads the backend summary, verifies the audit chain, seals the
assessment, verifies its immutable snapshot, drains the durable outbox, and creates and verifies
a signed audit checkpoint. Detector implementations remain independent and bounded.

An authenticated run may contain zero findings. Completion is represented by the signed run and
its authentication record, outside Finding Schema v1. The module remains `UNKNOWN`, receives no
module score, and contributes no assessment coverage. Its summary explicitly states that absence
of findings does not establish safety. A module with no run is separately described as not
assessed. No synthetic PASS/healthy finding is created.

## Offline demo

From the repository virtual environment:

```text
python scripts/demo_full_system.py --scenario clean
python scripts/demo_full_system.py --scenario concern
```

The command starts a loopback-only backend with a temporary SQLite database and temporary keys,
uses bounded locally generated image/ONNX fixtures, and performs no network download. The concern
scenario exercises dataset duplication, a model parameter anomaly, inference replay, and broad
multi-signal distribution shift. It prints finding/authentication counts, backend coverage and
assurance, disposition, audit status, lifecycle, snapshot, checkpoint, signed-run replay,
wrong-signature rejection, and signed-payload tamper rejection. The clean scenario intentionally
reports zero coverage and `UNAVAILABLE`; it does not claim safety.

## Live UI and APIs

With `VITE_DRISHTI_DEMO_MODE` unset or false, the existing analyst UI reads backend health,
assessment, summary, evidence, run/provenance, audit, model-registry, receipt, and checkpoint
routes. It does not recompute scores or dispositions. Details absent from backend responses are
shown as unavailable rather than fabricated. No browser signing or private-key storage is used.

## Offline assumptions and limitations

- Optional local ML resources degrade explicitly to unavailable; they are not downloaded.
- Detectors and assurance scoring are heuristics, not formal proof of safety or maliciousness.
- Total database destruction remains outside the local audit chain's recovery guarantees.
- Clean-tail audit assurance needs external checkpoint pinning.
- Checkpoint-key compromise can undermine checkpoint authenticity; no HSM or trusted timestamp
  authority is included.
- Authentication is a bearer-token MVP, not full RBAC.
- Database initialization uses `create_all`, not a production migration system.
- Deterministic digest identity is not physical-world authenticity.
- Passive cryptographic observation cannot establish all behavioral or causal properties.
